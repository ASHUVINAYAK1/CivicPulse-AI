# 1. Final Product Definition

## 1.1 Product vision

CivicPulse AI is an intelligent road infrastructure monitoring and predictive maintenance platform that transforms road damage reports, photographs, geographical information and historical maintenance records into actionable infrastructure intelligence.

The platform enables citizens and field inspectors to report road damage, uses computer vision to detect and classify damage, evaluates its potential severity, identifies geographical damage hotspots and recommends maintenance priorities.

Municipal administrators can manage incidents, assign repair teams, monitor maintenance activities and analyze historical and predicted road infrastructure conditions.

## 1.2 Problem statement

Municipal authorities often depend on manual inspections and unstructured complaints to identify road damage.

These processes create operational inefficiencies:

- Road damage may remain undetected for extended periods.
- Similar complaints may be registered multiple times.
- Maintenance priorities may be inconsistent.
- Infrastructure deterioration is difficult to track geographically.
- Historical maintenance information is not always converted into useful predictions.
- Authorities lack a consolidated view of infrastructure conditions.

CivicPulse AI addresses these problems by providing a centralized, AI-assisted road infrastructure monitoring and maintenance management system.

## 1.3 Product objectives

1. Automate road damage identification from photographs.
2. Classify road damage into meaningful categories.
3. Estimate preliminary damage severity.
4. Identify duplicate and geographically related incidents.
5. Discover road damage hotspots using clustering.
6. Predict maintenance urgency using structured ML models.
7. Forecast future incident volumes using time-series models.
8. Manage the complete maintenance lifecycle.
9. Provide explainable analytics to municipal administrators.
10. Maintain traceability of predictions, human verification and model versions.

## 1.4 Product scope

**Included in the initial release:**

- Road damage and pothole reporting.
- Image classification.
- Damage severity assessment.
- Duplicate incident detection.
- Incident prioritization.
- Geographical mapping.
- K-Means clustering.
- Predictive analytics.
- Maintenance task management.
- Administrative dashboards.
- Model evaluation and monitoring.

**Excluded from the initial release:**

- Other infrastructure categories such as drainage and streetlights.
- Autonomous repair authorization.
- Direct integration with municipal government systems.
- Automated traffic control.
- Physical road measurement without calibrated imagery.
- Mobile application distribution.

The frontend will be responsive so that citizens and inspectors can use it on mobile browsers.

- Allow long-running training experiments to execute independently of the web application.

The system should remain usable even when no GPU is available.

# 6. Machine Learning Architecture

The ML layer will be divided into five functional groups.

## 6.1 Group A — Classical Supervised Learning

| Algorithm | Business problem | Output |
|---|---|---|
| Linear Regression | Predict repair cost/duration | Numerical estimate |
| Logistic Regression | Predict maintenance urgency | Probability |
| SVM | Classify urgency/damage attributes | Class |
| Decision Tree | Explain urgency classification | Class + decision path |
| Random Forest | Predict maintenance priority | Class/probability |
| Bagging | Improve regression stability | Averaged prediction |
| AdaBoost | Improve classification performance | Class/probability |
| Gradient Boosting | Predict repair cost/duration | Numerical estimate |

### Model training workflow

1. Collect structured incident records.
2. Remove invalid entries.
3. Handle missing values.
4. Encode categorical variables.
5. Scale features where required.
6. Perform stratified or appropriate cross-validation.
7. Train baseline models.
8. Tune hyperparameters.
9. Compare metrics.
10. Register selected models.

### Feature engineering

Potential structured features:

- Damage category.
- Verified severity.
- Incident age.
- Number of nearby incidents.
- Historical recurrence count.
- Road classification, if available.
- Traffic information, if available.
- Region.
- Historical repair cost.
- Historical repair duration.

Avoid using information that would only become available after the prediction is supposed to be made. For example, actual repair cost cannot be an input when predicting repair cost.

## 6.2 Group B — Unsupervised Learning

### K-Means

Business objective: Discover geographically or operationally related road damage clusters.

Features may include:

- Latitude.
- Longitude.
- Incident frequency.
- Damage distribution.
- Verified severity.

Implementation:
- K-Means from scratch for the academic requirement.
- Euclidean distance.
- Centroid initialization.
- Cluster assignment.
- Centroid recalculation.
- Convergence detection.
- Elbow method.
- SSE calculation.

Important: Geographical distance should be calculated in a suitable projected coordinate system or with a geospatial distance metric. Raw latitude and longitude should not be treated as ordinary Euclidean coordinates for large geographical areas.

### PCA

Business objective: Reduce dimensionality of structured infrastructure features for analysis and visualization.

Steps:
1. Impute missing values.
2. Standardize features.
3. Calculate principal components.
4. Analyze explained variance.
5. Visualize in two dimensions.
6. Compare downstream model performance if PCA features are used for prediction.

## 6.3 Group C — Computer Vision

### CNN image classification

Initial target classes:

- D00: Longitudinal crack.
- D10: Transverse crack.
- D20: Alligator crack.
- D40: Pothole.

Use a compatible road damage dataset, such as RDD2022, after reviewing its annotations and licensing.

### Proposed CNN architecture

```text
Input Image
    |
Resize and Normalize
    |
Convolution Block 1
    |
ReLU + Max Pooling
    |
Convolution Block 2
    |
ReLU + Max Pooling
    |
Convolution Block 3
    |
ReLU + Max Pooling
    |
Global Average Pooling
    |
Dense Layer
    |
Dropout
    |
Softmax
    |
Damage Category
```

Use data augmentation such as:
- Horizontal flipping, when appropriate.
- Small rotations.
- Brightness adjustments.
- Random crops.

Evaluation:
- Macro precision.
- Macro recall.
- Macro F1.
- Confusion matrix.
- Per-class performance.

### Transfer learning

Compare at least two pretrained architectures:

- MobileNetV2.
- EfficientNetB0.
- ResNet50.

Recommended initial experiment:
- Freeze the pretrained backbone.
- Train a custom classification head.
- Unfreeze selected layers.
- Fine-tune with a lower learning rate.
- Compare against the baseline CNN.

For the final local inference service, prefer the model with the best balance of accuracy, inference latency and resource requirements.

### Advanced extension: Object detection

After image classification works, introduce an object detection model.

Possible architecture:
- YOLO family or another appropriately licensed detector.

Output:
- Bounding boxes.
- Damage category.
- Confidence.
- Image coordinates.

This is an advanced enhancement, not a dependency for the first release.

## 6.4 Group D — Neural Networks

### ANN

Purpose:
- Predict structured maintenance outcomes.
- Learn non-linear relationships.

Proposed architecture:

```text
Input Features
     |
Dense Layer (128)
     |
ReLU
     |
Dropout
     |
Dense Layer (64)
     |
ReLU
     |
Dense Layer (32)
     |
ReLU
     |
Output Layer
```

Choose output activation and loss based on the task:

- Binary classification: sigmoid + binary cross-entropy.
- Multiclass classification: softmax + categorical cross-entropy.
- Regression: linear output + suitable regression loss.

Training topics:
- Backpropagation.
- Gradient descent.
- Adam.
- Learning-rate scheduling.
- L1/L2 regularization.
- Dropout.
- Early stopping.

## 6.5 Group E — Time-Series Forecasting

### RNN/LSTM

Purpose:
Predict future road incident volumes.

Input:
- Historical weekly or monthly incidents.
- Regional incident trends.
- Damage category distribution.

Output:
- Predicted number of future incidents.

Proposed architecture:

```text
Historical Incident Sequences
           |
         LSTM
           |
      Dropout
           |
         LSTM
           |
       Dense Layer
           |
   Forecasted Incident Count
```

Evaluation:
- MAE.
- RMSE.
- Forecast-versus-actual plot.
- Comparison against naive and seasonal baselines.

Use chronological train/validation/test splitting. Do not randomly shuffle time-series records across these sets.

# 7. Model-to-Product Mapping

Not every experimental model needs to be exposed directly to end users.

| Product feature | Primary model | Supporting algorithms |
|---|---|---|
| Road damage detection | CNN / Transfer Learning | OpenCV |
| Damage severity | Validated structured classifier | Logistic Regression, SVM, Boosting |
| Maintenance priority | Random Forest / Gradient Boosting | Decision Tree |
| Cost estimation | Validated regression model | Linear Regression, Bagging |
| Duration estimation | Validated regression model | Gradient Boosting |
| Duplicate detection | Image/text similarity | Geographical matching |
| Geographic hotspots | K-Means / spatial clustering | PCA |
| Incident forecasting | LSTM | Baseline time-series models |

The severity model must be trained using independently verified severity labels. Damage category alone does not establish actual safety risk.

The priority engine should combine model output with configurable operational rules, and an authorized human must approve critical maintenance decisions.

# 9. Incident Processing Workflow

This is the most important end-to-end application workflow.

## 9.1 Citizen reporting

1. User logs in.
2. User opens Report Road Damage.
3. User uploads a photograph.
4. User selects or confirms the geographical location.
5. User adds a description.
6. Backend validates the request.
7. Incident is created.
8. Photograph is saved to MinIO.
9. An asynchronous AI analysis job is created.

## 9.2 AI analysis

1. Worker retrieves the pending job.
2. Image is downloaded from object storage.
3. Image is validated and preprocessed.
4. CNN predicts the damage category.
5. Prediction confidence is recorded.
6. Severity model generates a preliminary assessment, if available.
7. Duplicate detection checks nearby reports.
8. Priority engine calculates a recommendation.
9. Prediction records are saved.
10. Incident becomes available for inspector verification.

## 9.3 Human verification

1. Inspector opens the incident.
2. Inspector views the original image.
3. Inspector reviews AI predictions.
4. Inspector confirms or corrects the damage category.
5. Inspector selects the verified severity.
6. System records verification history.
7. Incident becomes eligible for maintenance prioritization.

## 9.4 Maintenance workflow

1. Administrator reviews the incident.
2. Administrator approves its maintenance priority.
3. Administrator assigns a team.
4. Maintenance team receives the task.
5. Team starts the repair.
6. Team uploads progress photographs.
7. Team records completion details.
8. Administrator verifies the repair.
9. Incident is closed.

```text

   |

   |

Feature Engineering

   |
```

- Use chronological splitting for forecasts.
- Preserve the original data and annotation provenance.

# 12. Model Evaluation and Acceptance Criteria

The project must use separate evaluation criteria for different tasks.

| Model type | Required metrics |
|---|---|
| Regression | MAE, RMSE, R² |
| Binary classification | Precision, Recall, F1, ROC-AUC |
| Multiclass classification | Macro F1, per-class recall |
| Image classification | Macro F1, confusion matrix |
| Object detection | mAP and IoU |
| Clustering | SSE, Silhouette Score |
| PCA | Explained variance |
| Forecasting | MAE, RMSE, MAPE where appropriate |

## Model acceptance policy

A model cannot become a production model simply because it trained successfully.

Each model must have:

1. A documented dataset.
2. A reproducible training procedure.
3. A validation report.
4. An independent test evaluation.
5. A model artifact.
6. A version identifier.
7. A defined inference contract.
8. Known limitations.

For severity and priority prediction, recall on the critical class is particularly important.

A model that misses serious incidents must not be considered successful merely because its overall accuracy is high.

# 13. Security and Reliability Requirements

## Authentication

- Password hashing using Argon2id or bcrypt.
- Secure session or token management.
- Role-based authorization.
- Refresh-token rotation if token-based authentication is selected.

## Image security

- Validate image formats.
- Limit upload sizes.
- Reject malformed files.
- Generate server-side object names.
- Do not trust original filenames.
- Restrict image access through authorized endpoints.

## Application security

- Validate all API inputs.
- Use parameterized database queries.
- Apply rate limits to sensitive endpoints.
- Protect administrative APIs.
- Store secrets in environment variables.
- Keep database backups.
- Record administrative changes.

## Reliability

- Background job retries.
- Idempotent job handling.
- Database transactions.
- Model version traceability.
- Graceful inference failure handling.
- Health-check endpoints.

# 18. Risks and Mitigation

| Risk | Mitigation |
|---|---|
| Insufficient severity labels | Create a documented annotation process |
| Dataset class imbalance | Class weighting and augmentation |
| Poor image classification | Compare multiple architectures |
| Synthetic data misleading results | Clearly separate synthetic and real data |
| Missing repair records | Treat cost and duration prediction as conditional modules |
| GPU limitations | CPU-compatible baseline and smaller models |
| Geographic clustering errors | Use PostGIS and appropriate distance metrics |
| Model overfitting | Cross-validation and independent test sets |
| False critical predictions | Human verification and calibrated thresholds |
| Large application complexity | Modular implementation and staged releases |

- A working citizen reporting interface.
- AI-powered image classification.
- Structured severity and priority assessment.
- Geographical incident intelligence.
- A functioning maintenance workflow.
- Model evaluation and explainability.
- Predictive analytics based on appropriate historical data.
- A reproducible ML experimentation pipeline.
- A complete locally deployable application.

CivicPulse AI is an AI-powered road infrastructure intelligence platform that combines computer vision, machine learning, geospatial analytics and predictive maintenance to help municipalities identify, prioritize and manage road damage more effectively.
